# 27 条踩坑与修复全记录

> **归档说明**：本文由项目全程技术复盘按"成果主线"重组而成，对应原复盘文档的相关章节（源文件 `archive/26中国软件杯_项目全程复盘.md`）。
> **性质**：基于代码、日志、产物实测的复盘记录，**非该阶段原始源码**；文中的代码片段为**原样节选（excerpt）**。

按"发现顺序 + 影响面"整理，这是本复盘最有价值的部分。

## T1. 加权采样被 basename 冲突静默丢弃（Step3）★★★

- **现象**：5383 行清单 → 只有 **1558** 张唯一图片，`thr_095×3` 加权完全失效
- **代码**：`dst_img = os.path.join(YOLO_TRAIN_IMG, os.path.basename(img_path))` + `if not os.path.exists(dst_img)`
- **磁盘证据**：`yolo_dataset/train/images` = 1558 = 70 + 1488（`thr_080 ⊇ thr_095` 的并集）
- **修复**：`train1_1.py` 用 `f"{base}_{idx:05d}{ext}"` 唯一命名 + `shutil.rmtree` 干净重建 + 换新目录名
- **验证**：`yolo_dataset_fixed/train/images` = **5383** ✅
- **收益**：mAP50 0.8766 → 0.8886（+1.2 点）
- **教训**：**任何"数据加权/过采样"必须落成物理文件**。清单里的重复行会被任何按文件去重的加载器吞掉，而且**静默无警告**。

## T2. X2Paddle DFL Slice 导致 GPU 输出全零（Step5/Step6）★★★

- **现象**：同一模型 CPU 推理正常，**GPU 推理输出全零**
- **根因**：X2Paddle 生成的 DFL 切片用动态索引（`Constant_7_cast` / `Mul_cast`），在 GPU 上求值为非法值（`end=0, start=4`）
- **修复**：因输出固定 `[1,4,8400]`/`[1,4,5376]`，**硬编码** `starts=[0], ends=[2]` / `starts=[2], ends=[4]`
- **⚠️ 未推广**：**Step9 的产物没有应用这个修复** ⇒ Step9 提交包是 CPU-only（FPS 会远低于 20）
- **教训**：**跨框架转换后必须 CPU/GPU 双向验证**。只测 CPU 会漏掉这类 bug；而且**修复必须记录成清单**，否则后续步骤会重犯

## T3. X2Paddle MaxPool dilation 断言过严（Step5）

- **现象**：转换直接失败
- **根因**：YOLOv8 SPPF 使用 `MaxPool(dilation=[1,1])`，X2Paddle 只允许 `dilation=None`
- **修复**：修改 `x2paddle/op_mapper/onnx2paddle/opset_legacy.py` ~L1980，放宽断言
- **⚠️ 两个 conda 环境都要打；重装 X2Paddle 会丢失**

## T4. Paddle 3.x int64/float32 类型不兼容（Step5）

- **现象**：转换后代码在 Paddle 3.x 下算术运算报错
- **修复**：在 `add`/`divide`/`multiply` 前显式 `cast(..., 'float32')`（**只在 v1 产物里，`_v2` 中已移除**）

## T5. PIR `.json` 格式在 Paddle 2.6.2 上 segfault（Step6）★★

- **现象**：`copy_to_cpu()` 时进程崩溃
- **根因**：`26cnsoft`（Paddle 3.3.1）的 X2Paddle 输出 PIR `.json` 格式，Paddle 2.6.2 推理引擎不兼容
- **修复**：**必须用 `26csresult` 的 X2Paddle 转换**，产出旧格式 `.pdmodel`
- **产物对照**：`x2paddle_512/`（废弃）vs `x2paddle_512_v2/`（可用）
- **教训**：**转换环境必须匹配推理环境的 Paddle 版本**

## T6. 改 IMGSZ 必须重导出模型（Step6）★★★

- **现象**：把 `IMGSZ` 从 640 改成 512 后 `reshape` 报错 `5376 != 8400`
- **根因**：检测头内网格数硬编码（640→8400，512→5376）
- **修复**：`export(format="onnx", imgsz=512, opset=12)` + 重跑 X2Paddle + `convert_model.py` 重新 `paddle.jit.save`
- **验证**：`paddle.slice` 的 `reshape(shape=[1,4,16,5376])` 与 `model/predict.py` 的 `IMGSZ=512` 一致

## T7. AdamW `momentum=None` 导致训练异常（Step4）★★

- **代码**：`momentum=0.937 if opt=='SGD' else None`
- **现象**：日志反复出现 `⚠️ yolov8m_AdamW_1e-4 未生成best.pt`，跑了 6.8 小时看似白跑
- **真相**：权重其实生成了（`test.py` 找到了），是**脚本的路径判断有误**（`save_dir/weights/` vs `save_dir/train/weights/`）
- **修复**：`train1_1.py` → `momentum_val = 0.937 if opt == 'SGD' else 0.9`
- **教训**：① Ultralytics 的 `momentum` 对 AdamW 也有语义（映射到 beta1），不能留空；② **"文件没生成"要先怀疑检查路径，而不是训练失败**

## T8. Windows 下 YOLO `train.txt` 列表式配置失效（Step7）★★

- **现象**：`train: 892 images, 0 backgrounds`（应为 892 张都有标签），`cls_loss=237.6`
- **根因**：`os.sep`（`\`）与 YOLO 期望的路径分隔符不匹配
- **修复**：改用**目录格式**（`train: train` / `val: val`），依赖 YOLO 内部的 `\images\` → `\labels\` 字符串替换
- **注意**：替换机制要求路径中**完整包含 `\images\`**

## T9. AMP check 反复下载模型卡住（Step7）

- **现象**：训练启动时反复 curl 超时下载 `yolo26n.pt`，每次约 3 分钟
- **修复**：`amp=False` 跳过 AMP 检查
- **副作用**：`amp=False` 只在 `step4/train1_1.py` / `step7` / `step8` 出现，Step3 与 Step4 首版是默认 AMP 开 ⇒ **它们的数值表现不可直接比较**

## T10. 硬链接跨卷失败 / 硬链接导致 val 为空（Step7/Step8）

- **现象 A**：`os.link` 跨分区抛 `OSError`
- **现象 B**：`dataN/val` 为空，YOLO 报 "No images found in val"
- **修复**：统一封装 `hardlink_or_copy(src, dst)`，`except (OSError, NotImplementedError)` 时回退 `shutil.copy2`
- **⚠️ 唯一例外**：`step8/tool/init.py` 的 `data1/images` 用的是 `copy2`（这里正是 T10-B 的现场）

## T11. 僵尸 python 进程累积拖慢训练（Step8）★★

- **现象**：物理内存 28/32 GB，训练从 0.3 s/batch 恶化到 **30 s/batch**（100 倍）
- **修复**：定期 `taskkill` 清理残留 `python.exe`，检查 `nvidia-smi`
- **教训**：**长跑训练前先检查系统资源**，"训练突然变慢 100 倍"通常是环境问题不是模型问题

## T12. OOM 重试分支漏传参数（Step8）★★★

- **代码**：主路径传了 `iou=iou_val`，**OOM 重试路径没传**，且把 `epochs` 重置成 `HP["epochs"]`
- **日志证据**：**所有 12 个 train 日志都写 `Batch used: 8`** ⇒ 每轮都走了 OOM 分支 ⇒ **`--iou 0.9` 从未生效**
- **后果**：原文档基于"Phase 2 = IoU 0.9 vs Phase 3 = IoU 0.7"的整个对比实验**在方法学上不成立**
- **教训**：**异常/重试分支必须传齐所有参数**。否则参数会**静默回退默认值**，产生无法从日志发现的错误结论

## T13. Resume 失败（Step8）

- **现象**：恢复 checkpoint 时 CUDA OOM
- **修复**：**不 resume**，直接用 `last.pt` 作为 `weights` 参数重新训练
- **⚠️ 且 `resume=True` 时 `project`/`name`/`epochs` 参数都是 no-op**（Ultralytics 从 checkpoint 恢复原始参数）

## T14. 过采样命名冲突（Step8）★★

- **现象**：`_r` 后缀文件被反复追加（`_r2`、`_r10`、`_r11`、`_r12`）
- **根因**：重跑过采样时没有清空输出目录，计数器从上次状态继续
- **后果**：`data10/train/images` 膨胀到 **7240 张**（其他轮 ~2180），该轮训练分布与其他轮不可比
- **⚠️ 声称的修复（`defaultdict(int)`）在任何现存脚本里都不存在** —— 因为生成脚本本身丢失了
- **建议修复**：用 `defaultdict(int)` 严格从 0 计数，并在 rebuild 开始时 `shutil.rmtree(out_dir)`

## T15. LabelMe JSON 坐标方向不定（Step7/Step8）

- **现象**：`points: [[x1,y1],[x2,y2]]` 中可能 `x1 > x2`
- **修复**：`xmin, xmax = min(x1,x2), max(x1,x2)`（`build4.py` / `rebuild.py` 均已处理）

## T16. `build4.py` 只取 `shapes[0]`（Step7）

- **代码**：`s = shapes[0]`
- **后果**：一图多框时**第二个之后的框被静默丢弃**
- **对比**：Step8 的 `rebuild.py` 遍历**所有** `shapes` ✅
- **未暴露原因**：9 张人工修正样本恰好都是单框

## T17. `cv2.imread` 无法读中文路径（7.19 演示工程）★

- **现象**：读取 `E:\desktop\school\26中国软件杯\...` 下的图片失败
- **修复**：`np.frombuffer(open(p,'rb').read(), np.uint8)` + `cv2.imdecode(..., cv2.IMREAD_COLOR)`

## T18. 本地 GPU 完全不可用（贯穿全程）★★★

- **现象**：Paddle 2.6.2（CUDA 11.8 runtime）不支持 RTX 5060 Ti（CC 12.0），GPU 推理输出全零或 segfault
- **影响**：**本地无法测速**，FPS 只能靠平台反馈
- **后果**：Step7 的"预估 FPS 35–45"从未被验证，直接影响了后续路线决策

## T19. `sample100` 不代表平台分布（Step6）★★★

- **现象**：本地 F1 0.9749 vs 平台 F1 0.37529（差 2.6 倍）
- **影响**：本地只能做**功能验证**，精度判断必须依赖平台
- **教训**：**本地验证集必须与评测集同分布**。这是本项目最大的评估方法论失误

## T20. 竖棍形幻觉框（Step9）★★★

- **现象**：**196 张图（6.9%）** 的"面积最大框"是极细高的幻觉框
- **修复**：三级降级的形状先验算法（见 12.5）
- **⚠️ 修复效果无法量化**：`step9/log/` 为空，只剩 `was 196` 这一个数字
- **教训**：**"面积最大"这个规则本身有漏洞** —— 面积大不等于目标大。多框模型容易被细长背景纹理骗到（**reward hacking**）

## T21. 收敛判定与训练时序错位（Step8）★★

- **现象**：R9/R10/R13 的 `converge.py` 时间戳**早于**对应训练日志；部分轮次只有 gen 没有 train
- **后果**：`converge.py` 比较的是"上一轮模型的输出"，收敛曲线与训练曲线不同步
- **教训**：自动化流水线必须保证"训练完成 → 推理 → 收敛判定 → 合并"的**严格串行**，且日志时间戳可验证

## T22. 验证集泄漏（Step8）★★★

- **现象**：`data12` 的 `train ∩ val = 264` 张，另有 96 张 val 在 train 里有 `_r2` 孪生
- **根因**：train 是从过采样/欠采样规则**组装**的，不是作为 val 的**补集**算出来的
- **后果**：**验证 mAP50 虚高**，直接解释了为什么 0.94~0.98 的验证分数没有实用收益
- **对照**：`step7/data4` 没有重叠（一次 shuffle 后的不相交切片）✅

## T23. `build.py` 的字典序排序 bug（Step8）

- **代码**：`last_round = sorted(STEP8.glob("pseudo_round*"))[-1]`
- **问题**：字典序下 `pseudo_round9` > `pseudo_round15`。在 ≥10 轮时"最后一轮"会选错
- **当前是否触发**：`build.py` 在 R4 时运行（那时只有 `pseudo_round1~4`），所以**未触发**，但是潜在 bug
- **修复**：用 `max(..., key=lambda p: int(p.name.replace("pseudo_round","")))`

## T24. 三个"被记录但完全无效"的实验（Step2）★★★

- **`Exp-D2_weighted`**：`_current_weights` 全局变量从未被赋值 → 加权损失 = 无权损失
- **`Exp2-B`（标签平滑 0.1）**：`label_smoothing` 从未传给损失函数
- **`Exp2-E`（伪标签权重衰减）**：`pseudo_w` 只被插值进日志字符串，从不乘任何损失
- **后果**：`S2conclusion.md` 的结论 F3"标签平滑有害"**完全没有依据**；"Exp2-E 同模式"是同义反复
- **教训**：**"配置存在" ≠ "配置生效"**。跑消融前必须验证每个变量真的改变了行为（例如打一行 `assert weights is not None`）

## T25. `annotate.py` 的置信度统计是死胡同（Step1）

- **现象**：`annotate.py` 输出详尽的置信度直方图（0.01 步长、7 个阈值档位）
- **但**：`gen_labels.py` 用的阈值 `[0.99,0.95,0.90,0.80,0.75]` 是**硬编码**的，与这份统计无关
- **教训**：**统计产出了就要消费它**，否则是纯粹的计算浪费

## T26. `split.json` 与 `real_val.txt` 两套验证集（Step2）★★

- **现象**：Step2 用 20 张随机（`split.json`），Step3/4 用 30 张时序（`real_val.txt`）
- **后果**：Step2 的 F1 与 Step3/4 的 mAP50 **不可比**，跨框架的"前后对比"被混淆
- **教训**：**验证集必须一次定义、全局唯一**

## T27. F1 评估跨图匹配（Step1/Step2）★★★

- **代码**：`train2.py` / `eval.py` / `train_exp.py` / `train_exp2.py` 的 `evaluate_f1()` 把整个验证集的 GT 和预测池化，**不绑 image id**
- **后果**：A 图的预测可以匹配 B 图的真值 ⇒ TP/FP 计数任意膨胀/收缩
- **对照**：`step6/eval.py` **做对了**（`if ge[0] != pe[0]: continue`）
- **教训**：**评估代码比训练代码更需要 review**。一个"看起来合理"的贪心匹配可能是完全错误的
