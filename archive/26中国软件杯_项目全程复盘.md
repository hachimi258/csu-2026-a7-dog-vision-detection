## 一、项目目标与赛制

### 1.1 赛题背景

赛题 **A7：基于机器狗的视觉目标检测**，以宇树 Go2 Edu 机器狗为物理平台、百度飞桨 PaddlePaddle 为视觉框架，通过 AR 增强现实方式在标准场地上叠加数字目标，模拟消防侦察场景。

### 1.2 两个榜单的任务差异

| 维度 | A 榜 | B 榜 |
|:---|:---|:---|
| 任务 | 3 类目标检测 | 单类火焰检测 |
| 类别 | `battery`(1) / `board`(2) / `fire`(3) | `firebig`(1) |
| 每图输出 | 所有检测框 | **仅 1 个框**（面积最大的那处火焰） |
| 图像 | 1920×1080 VR 帧 | 640×480 AR 合成场景 JPEG |
| 训练数据 | `A_train` 405 张（LabelMe 人工标注） | 无标注池 2827 张 `captures` + 100 张带标注抽样 `sample100` |
| 评测指标 | 3 类平均 F1 | 单类 F1 |
| IoU 匹配阈值 | 0.5 | 0.5 |
| 速度门槛 | FPS ≥ 20 | FPS ≥ 20（4544 张 / 总耗时；低于则综合分强制为 0） |
| 框架要求 | PaddlePaddle 静态图 | PaddlePaddle 静态图（`.pdmodel` + `.pdiparams`） |
| 模型大小 | `model/` ≤ 200 MB | `model/` ≤ 200 MB |

### 1.3 提交规范（两榜共通）

```
submission.zip
├── predict.py            # 入口：python predict.py <data_txt> <result_json>
└── model/
    ├── infer_cfg.yml
    ├── model.pdmodel
    └── model.pdiparams
```

输出 JSON：

```json
{"result":[{"image_id":"frame_00000","type":1,"x":120.5,"y":45.0,
            "width":200.0,"height":180.0,"segmentation":[]}]}
```

- `image_id` = 文件名（不含扩展名）
- `x, y` = 左上角坐标；`width, height` = 宽高
- 无目标则不添加条目
- `predict.py` 必须返回码 0 且写出合法 JSON

### 1.4 项目自定的三条代码规则（`context/rule.txt`）

1. 所有代码名称尽可能极致简短（`init.py` / `train.py` / `gen.py` / `merge.py` / `converge.py` / `view.py` / `pack.py` / `eval.py` / `export.py`）
2. 每个 step 的脚本必须把关键信息日志写入 `{step}/log/`，命名为 `{时间戳}_{脚本名}.log`，只留关键信息
3. 代码不得影响其他 step，原则上只复制数据、不删改数据

> 这三条规则在整个 B 榜阶段被大体严格执行，是项目能快速迭代的工程基础。（例外：Step9 全部脚本未写日志。）

### 3.6 ⚠️ A 榜遗留问题（原文档未提及）

**提交包的 `infer_cfg.yml` 里 `label_list` 仍是 COCO 的 80 类**（`person, bicycle, car, ... toothbrush`），而不是 `battery/board/fire`。

**为什么没有导致失败**：`predict.py` 从不读取 `label_list`，`type` 字段直接由 `class_id + 1` 数值计算，而类别数已固化在权重中（`configs/dataset.yml` 是 `num_classes: 3`）。所以 80 类名只是"死配置"，纯粹是导出时忘了替换。**这是一个高风险巧合，不是设计**。

另外 `7.19/A榜_model/infer_cfg.yml`（1211 B）与提交包完全一致（同样 80 类），说明这个配置从导出起就没被修正过。对比 `7.19/B榜_model/infer_cfg.yml` 只有 0.3 KB 且 `label_list: [firebig]` —— B 榜的 `infer_cfg.yml` 是脚本生成的（`step7/tool/pack.py` 会写入），所以正确；A 榜直接用了 PaddleDetection 导出的原始文件。

## 四、B 榜 Step1：Faster R-CNN 自动标注器

### 4.1 目的

只有 100 张真实标注（`sample100`）可用。Step1 训练一个"够用"的检测器，用它给 2827 张无标注图打伪标签，作为整个自训练（self-training）链路的起点。

**关键定位**：Step1 的模型是**教师（teacher）**，不是最终提交模型。最终提交用的是 step3/step4 训练的 YOLOv8m。

### 4.2 ⚠️ 架构勘误：不是 YOLO，是 Faster R-CNN

`S1-5conclusion.md` 第 55 行称"基于 `sample100` 训练 **YOLOv5-like** 模型"，**这是错误的**。

代码证据（`step1/train.py`）：

```python
from torchvision.models.detection import fasterrcnn_resnet50_fpn_v2, \
    FasterRCNN_ResNet50_FPN_V2_Weights
from torchvision.models.detection.faster_rcnn import FastRCNNPredictor

weights = FasterRCNN_ResNet50_FPN_V2_Weights.DEFAULT
model = fasterrcnn_resnet50_fpn_v2(weights=weights)
in_features = model.roi_heads.box_predictor.cls_score.in_features
model.roi_heads.box_predictor = FastRCNNPredictor(in_features, num_classes)
```

日志中出现的三种 loss 正是 Faster R-CNN 的损失：

```
Epoch 10/150 | Loss: 0.0112 (cls: 0.0053, box: 0.0053, rpn: 0.0001)
                                          ↑        ↑          ↑
                          loss_classifier  loss_box_reg  loss_rpn_box_reg
```

| torchvision 损失键 | 来源 | 是否被记录 |
|:---|:---|:---|
| `loss_classifier` | RoI 头 —— Fast R-CNN 分类 | ✅ `cls` |
| `loss_box_reg` | RoI 头 —— Fast R-CNN 框回归 | ✅ `box` |
| `loss_objectness` | RPN —— 二分类 objectness | ❌ **从不记录** |
| `loss_rpn_box_reg` | RPN —— 提议框回归 | ✅ `rpn` |

> **副作用**：打印的"总损失"是四项之和，但只显示三项，所以日志里 `总损失 > cls+box+rpn`。这是一个日志不一致。

**架构细节**：

- **Backbone**：ResNet-50 + FPN，**v2 变体**（torchvision 改进版配方）
- **Head**：标准 `FasterRCNN` —— RPN + `RoIHeads`（MultiScaleRoIAlign + box head + `FastRCNNPredictor`）
- **Anchor**：**全项目没有任何手工定义 anchor**。使用 torchvision 默认值：5 种尺度 `(32,64,128,256,512)` × 3 种长宽比 `(0.5,1.0,2.0)` = 每层每位置 15 个 anchor，覆盖 5 个 FPN 层
- **类别数**：`num_classes = 1 + 1 = 2`（背景 + `firebig`），`FastRCNNPredictor(in_features=1024, num_classes=2)`
- **输入处理**：全程 `transform=None`，只有 `transforms.functional.to_tensor` → **[0,1] float，无归一化、无 resize、无增强**。torchvision 内部的 `GeneralizedRCNNTransform` 做 `min_size=800, max_size=1333` 缩放。对 640×480 的图得到 **1067×800**（scale = 800/480 ≈ 1.667）。
- **类别发现**：从数据里读（`_get_classes()` 收集所有 `<name>` 文本排序），背景固定 index 0

### 4.3 Step1 参数

> **注意**：`train2.py` 用 `fasterrcnn_resnet50_fpn_v2(num_classes=num_classes)` **不带 COCO 权重**构造模型，然后 `load_state_dict(model.pth)`。即**这一步完全没有用 COCO 预训练**，模型完全由 `train.py` 的权重定义。
>
> 另外**从不保存 optimizer state**，所以"续训"实际上是"重启学习率调度"。`train2.py` 有意用 0.001 重新开始 `StepLR(step_size=30)`。

### 4.4 ⚠️ 严重方法论缺陷：F1 评估跨图匹配

`train2.py` / `eval.py` / `train_exp.py` / `train_exp2.py` 共用的 `evaluate_f1()` 逻辑：

1. 模型 `eval()`，在验证集上 `no_grad()` 推理
2. **把整个验证集所有 GT 框和所有预测框（带分数）分别池化成两个扁平列表**（不记录来自哪张图）
3. 预测框按分数降序
4. 贪心匹配：每个预测框与**池中所有 GT 框**算 IoU，取最大；若 ≥0.5 且该 GT 未被匹配过，则记 TP
5. `tp = 分数≥0.5 的 TP 数`，`fp = 分数≥0.5 的非 TP 数`，`fn = n_gt - tp`

**致命问题**：GT 列表和预测列表**都没有绑定 image id**，匹配是在池化集合上做的，**所以 A 图的预测框可以匹配 B 图的真值框**。TP/FP 计数会任意膨胀或收缩。

**对照证据**：`step6/eval.py` 里作者**把这件事做对了**——它用 `if ge[0] != pe[0]: continue` 做了同图约束。所以 step1/step2 的跨图 bug 是真实缺陷，不是理解偏差。

> **结论**：**Step1 和 Step2 的所有 F1 数字都不可作为权威指标引用**。Step6 的 F1 是正确计算的。

`step1/eval.py` 还有额外的指标问题：

- **手写梯形左黎曼和 AP**（非 VOC 11 点、非全点插值），且**没有做 precision envelope（单调递减包络）**，系统性偏低
- 固定的 conf 阈值扫描存在**顺序缺陷**：一个 GT 框可能先被低分预测框"吃掉"（匹配时不看阈值），导致高分预测框无法再匹配，压低召回
- `micro_f1 = 2*Σ(R*P)/(ΣR+ΣP)` **不是真正的 micro-F1**（那是类内平均的调和平均），`macro_f1 = np.mean(f1s)` 才是正确的宏平均
- 若某类无 GT，强制 `ap=0.0, f1=0.0`（即使也没有预测），会拖低 mAP

### 5.2 流水线拆解

**① `infer.py`**：Faster R-CNN 对 2827 张推理，**保存原始框不设阈值**，结果序列化为 `pre_data/raw_predictions.pkl`：

**② `gen_labels.py`**：从 pkl 生成多阈值 XML

```python
thresholds = [0.99, 0.95, 0.90, 0.80, 0.75]
out_dir = data_root / f"thr_{int(thr*100):03d}"
for img_id, pred in raw.items():
    areas = (boxes[:,2]-boxes[:,0]) * (boxes[:,3]-boxes[:,1])
    max_idx = areas.argmax()                 # ⭐ 每图只取「面积最大」的框
    max_score = scores[max_idx]
    if max_score >= thr:
        # 坐标硬裁剪到 [0,639]×[0,479]
        box = boxes[max_idx]
        labels[max_idx] → class_name（缺失时默认 "firebig"）
        写 XML 到 data/thr_{int(thr*100):03d}/{img_id}.xml
# 同时输出 conf_map.json：{img_id: max_score}  用于 Exp-D2 逐框置信度加权
# 同时输出 split.json：sample100 固定 80/20 划分（seed=42）
```

**这一步定义了整个项目的核心不变式**：**任务被简化为"单类 + 每图一个最大面积框"的定位问题**。`max_idx`/`max_score` 是从**所有**预测框（不分类别）算出来的。

**⚠️ 硬编码 640×480**：坐标裁剪用 `min(x1, 639)` / `min(y1, 479)`，`create_xml()` 的默认 `width=640, height=480`。**脚本从不打开图片检查尺寸**（它只有 pkl，没有图像尺寸信息）。若某张 capture 尺寸不同，框会被裁到错误的坐标系且 XML 的 `<size>` 会撒谎。这只是因为 `captures` 恰好全是 640×480 才没出事。

### 5.3 ⚠️⚠️ 三个"被记录但完全无效"的实验（原文档的核心结论建立在它们之上）

这是整个 Step2 最严重的问题。

| 实验 | 文件 | 为什么不生效 |
|:---|:---|:---|
| **`Exp-D2_weighted`** | `train_exp.py` | 全局变量 `_current_weights` **从未被赋值**。代码只在 `weighted_fastrcnn_loss` 里 `global _current_weights` 然后**只读**，所以 `'_current_weights' in globals()` 恒为 `False`，`weights` 恒为 `None`，回退到 `torch.ones_like(labels)` —— **加权损失与无权损失数值完全相同**。`VOCDataset` 认真地把 `target['weights'] = confs` 塞进 target，但**训练循环从不读它**。<br>**⇒ `Exp-D2_weighted` 是 `Exp-thr_080` 的重复实验。**<br>即使 `_current_weights` 被填上，`target['weights']` 是**按原始标注**粒度，而 `labels`/`box_regression` 是**按采样后的 RoI** 粒度（`sample_positive`/`sample_negative` 会重排和复制），`weights[pos]` 的索引是形状/顺序错配的。 |
| **`Exp2-B`（标签平滑 0.1）** | `train_exp2.py` | `label_smoothing` 只写在 `EXPERIMENTS` 配置字典里，**从未传给任何损失函数**。torchvision 内部的 `fastrcnn_loss` 调用 `F.cross_entropy(..., reduction="sum") / N`，**没有 `label_smoothing` 参数**。<br>**⇒ `Exp2-B` 与 `Exp2-A` 功能完全相同。** |
| **`Exp2-E`（伪标签权重衰减）** | `train_exp2.py` | `pseudo_w = get_pseudo_weight(epoch, train_cfg)` 每个 epoch 都算，但**只被插值进日志字符串**（`f"...(pseudo_weight={pseudo_w:.2f})"`）。它从不乘任何损失项、不影响采样器、不改数据集权重。<br>**⇒ `Exp2-E` 与 `Exp2-A` 功能完全相同。** |

**后果**：

- `S2conclusion.md` 的结论 **F3「标签平滑（Label Smoothing=0.1）在本数据集上有害」完全没有依据**——它比较的是两个相同的实验，0.7879 vs 0.8718 的差异纯属训练随机性
- 表 F1 行"Exp2-A（30 轮）Epoch 1 达 0.8718"与"Exp2-E 同模式"——**Exp2-E 就是 Exp2-A**，所以"同模式"是同义反复
- `exp_weights/` 里恰好只有 `Exp2-A_best.pth` / `Exp2-B_best.pth` / `Exp2-E_best.pth` 三个文件，而按上面的分析**这三个应该产出几乎相同的 F1**——这正是"三个实验一致，所以结论稳健"这种**极具误导性**的结果形态

```python
mixed_pairs = pseudo_095_pairs * 3 + pseudo_080_pairs
```

```
最优数据集 = (thr_095 的图片) × 3 + (thr_080 的图片) × 1
           = 1275 × 3  +  1488 × 1
           = 3825      +  1488      = 5313 行
```

磁盘实测：`real_train.txt = 70` 行、`real_val.txt = 30` 行、`pseudo_mixed_optimal.txt = 5313` 行 ✅ —— 算术精确对上。

`metadata.json` 记录了 `images_count`、真实样本数、`val_indices`、`val_files`、伪标签数、`mixed_formula: "thr_095 x 3 + thr_080 x 1"`、三个清单路径。

### 5.7 ⚠️ 勘误：1275 vs 1887 的分母问题

| 来源 | thr≥0.95 的 XML 数 |
|:---|:---|
| Step1 `annotate.log`（阈值 0.95 直出） | **1887**（框数） |
| Step2 `final_data/annotations/pseudo/thr_095/` | **1275**（图片数） |

**原因**：Step1 把模型**所有 ≥0.95 的框**都写进 XML（一图可能多个 object）；Step2 的 `gen_labels.py` **每图只保留面积最大的那一个框**（`areas.argmax()`），所以 1887 框 → 1275 张图。

**这个差异恰好符合赛制**（每图只需 1 个框），但意味着：
- 原文档中"1488 张有目标 / 1339 张无目标"（Step1 口径）与"thr_095 共 1275 个"（Step2 口径）**是两个不同分母**，不是矛盾，但原文没说清
- Step2 的 1275 + 1488 说明：**阈值的实际语义变成了"面积最大框的置信度"**，而不是"任意框的置信度"。这个语义变化是合理的，但没有被声明

## 六、B 榜 Step3：切换到 YOLO 与架构筛选

### 6.1 目的

### 6.2 ⚠️ 第一次尝试的致命 bug（`train1.py`）

**现象**：清单 5383 行，但训练时只有 **1558 张唯一图片**。

**根因**：

```python
img_name = os.path.basename(img_path)

    shutil.copy2(img_path, dst_img)
```

因为 `pseudo_mixed_optimal.txt` 故意把同一张图列了 **3 次**（`thr_095×3`），而目标文件名只用 basename，所以第 2、3 次命中 `os.path.exists` 被**静默跳过**。标签同理。

**磁盘实测（这是被证明的，不是推断）**：

| 路径 | 文件数 |
|:---|:---|
| `step3/yolo_dataset/train/images` | **1558** |
| `step3/yolo_dataset/train/labels` | **1558** |
| 期望（清单） | 5383 |

实际 = 70 真实 + (thr_095 ∪ thr_080 的唯一 stem 数) = 70 + **1488** = **1558** ✅（`thr_080 ⊇ thr_095`，所以并集是 1488 个 stem）

> **Step2 整个重采样假设在框架切换边界上被静默丢弃了**，没有任何报错或警告。这就是 `train1_1.py` 存在的直接原因。
>
> 雪上加霜：`train1.py` 里的 `random.shuffle(all_train)` **没有设种子**，所以哪次重复"赢得"basename 竞争是不确定的——同一脚本两次运行的 1558 张子集可能不同。

**其他 bug**：

- **模型名拼错**：`candidate_models = ["yolov10m.pt", "yolov11m.pt", "yolov8m.pt", "yolov11s.pt", "yolov8n.pt"]`。正确名字是 `yolo11m.pt` / `yolo11s.pt`（无 "v"）。两者都在 `YOLO(name)` 抛异常并被 `except Exception: return None` 吞掉，所以 **5 个候选里只有 3 个真训练**（`yolov10m` / `yolov8m` / `yolov8n`）。

### 6.6 `train1_2.py` 的续训机制（值得学习的工程技巧）

1. 若 `yolo_dataset_fixed/dataset.yaml` 缺失则中止（提示先跑 `train1_1.py`）
2. `result_dirs = glob(step3/result/20*)`；`latest_result = max(result_dirs)` —— **在 `YYYYmmdd_HHMMSS` 固定宽度命名上做字符串 max 就是时间序**（一个巧妙的技巧，但强依赖命名格式）
3. 按磁盘上已存在的文件做三路决策：
   - `weights/best.pt` 存在 → **跳过训练**，只 `model.val()` 并报告
   - 否则 `weights/last.pt` 存在 → `resume = True`，`model.train(resume=True, ...)`
   - 都不存在 → 全新 `model.train(...)`
4. **OOM 处理很周到**：捕获含 `"out of memory"` 的 `RuntimeError` → 用 `batch=8` 重试；**若之前在 resume 状态，则放弃 resume 从头开始**（因为无法在续训时改 batch）
5. 写 `summary_continue.txt`（不覆盖原始 `summary.txt`）

**⚠️ 但 `resume=True` 时 `project`/`name` 参数是无效的** —— Ultralytics 会从 checkpoint 恢复原始训练参数，忽略这两个覆盖项。代码注释声称它们"确保保存位置正确"，实际是 no-op。另外 `resume=True` 也会**恢复原始 `epochs`**，无法用它延长训练。

## 七、B 榜 Step4：超参数调优

### 7.1 目的

在固定数据集（`yolo_dataset_fixed`）上对候选模型搜索**优化器 × 学习率**组合，产出精度最高的权重。

### 7.2 实验设计（`train1.py`）

```python
models      = ["yolov8m", "yolo11m"]
optimizers  = ["SGD", "AdamW"]
lrs         = [1e-4, 5e-4]
# 8 组组合，每组 epochs=5, imgsz=640, batch=16 (OOM→8)
```

**初始化方式**：`find_step3_best(model_key)` 在 `step3/result/20*` 中取最新目录，用**子串匹配**找 `best.pt`，然后 `YOLO(pretrain_path)`。代码注释精确说明了意图：**"仅加载权重，优化器自动重置"** —— 加载原始权重（而非训练 checkpoint）会丢弃 step3 的 SGD 动量与调度器状态，让每个网格单元都从新优化器开始。这是跑这类消融的正确做法。

### 7.3 训练超参数（`train1.py`）

| 参数 | 值 |
|:---|:---|
| `epochs` | **5** |
| `imgsz` | **640** |
| `batch` | **16**（OOM → 8） |
| `patience` | **`epochs`** = 5 → **等效禁用早停**（`patience` 等于总轮数即保证跑满） |
| `save_period` | **1**（每轮存 checkpoint） |
| `seed` | **42** |
| `lr0` | **1e-4 或 5e-4** |
| `optimizer` | **`'SGD'` 或 `'AdamW'`** |
| `weight_decay` | **SGD → 0.0005；AdamW → 0.01**（AdaM 家族用更大 wd，是正确的实践） |
| `momentum` | **SGD → 0.937；AdamW → `None`** ← **BUG** |
| `device` / `workers` | 0 / 4 |

**目录命名**：

```python
save_name = f"{model_key}_{opt}_{lr:.0e}".replace('e-0', 'e-')
# yolov8m_SGD_1e-4  （{lr:.0e} 得 "1e-04"，replace 归一化为 "1e-4"）
save_dir  = os.path.join(MODEL_DIR, ts_root, save_name)
```

磁盘验证：`step5/export.py` 硬编码了 `step5\best1\yolov8m_AdamW_1e-4\train\weights\best.pt` —— **证实网格的赢家是 YOLOv8m + AdamW + lr 1e-4**。

**⚠️ 目录层级偏差**：`train1.py` 里 `ts_root` 是在 `run_exp()` **内部**计算的，所以 8 个格子落在 **8 个不同的时间戳目录**里，而不是一个运行级目录。`train1_1.py` 通过把 `root_ts` 提到 `main()` 修复了这个问题。

### 7.4 ⚠️ `momentum=None` bug

```python
momentum=0.937 if opt=='SGD' else None,
```

对 AdamW 传 `momentum=None` 对 Ultralytics 的优化器构建器是非法值（它期望 float，`None` 不是合法的 beta1 覆盖）。这个 bug **没有硬崩溃**（所以实验还是跑出了权重），但是潜在的失败点。

**`train1_1.py` 显式修复**：

```python
momentum_val = 0.937 if opt == 'SGD' else 0.9
# 注释：====== 修正：对于AdamW，momentum不能为None，设为0.9（默认beta1） ======
```

**同时新增 `amp=False`**（主路径与 OOM 重试路径都加）。这**关闭了自动混合精度** —— 一个明显的环境适配 hack（很可能是为了规避 RTX 5060 + 夜间版 torch 组合下的 NaN/溢出）。代价是速度，收益是消除一整类不稳定。

> **注意**：`amp=False` **只出现在 `train1_1.py`**。`step3/train1*.py` 和 `step4/train1.py` 都跑在 Ultralytics 默认 AMP 开的状态下。所以 Step3 与 Step4 的数值表现**不可直接比较**。

### 7.5 ⚠️ 日志解析式断点续传（`train1_1.py`）

作者用**解析上一次运行的日志文件**来判断哪些实验已完成 —— 一个不依赖文件系统的进度追踪器。

```python
start_pattern  = re.compile(r'>>> 开始 (\w+) \| (\w+) \| lr=([\d.eE+-]+)')
finish_pattern = re.compile(r'(✅|⚠️)\s+(\S+)\s+(?:最佳mAP50 = ([\d.]+)|未生成best\.pt)')
```

两遍扫描：先收集所有 `started` 三元组，再收集 `completed`（带 map50 值，或 `None` 表示 `⚠️ … 未生成best.pt`）。`unfinished = started - set(completed)`，实际运行列表 = `all_combinations - completed`。

从完成行恢复 key：

```python
parts = name.split('_')
model, opt = parts[0], parts[1]
lr_part = '_'.join(parts[2:])          # "1e-4"
lr = float(lr_part.replace('e-','e-')) # ← no-op replace（作者大概想归一化 e-04 → e-4）
```

**只从 `*_train1.log` 恢复**，所以 `train1_1.py` 自己（日志名 `*_train1_1.log`）无法被续传 —— 一个有意设计的一跳链。

> **⚠️ 极度脆弱**：这个续传逻辑依赖日志字符串的精确 emoji + 空格（`✅ {save_name} 最佳mAP50 = {map50:.4f}`）。任何日志格式改动都会**静默地**让 `completed` 变空，从而**全量重跑**。这是一个"沉默失效"的设计。

### 7.7 ⚠️⚠️ Step4 最严重的问题：同参数两次运行差 3.5 个点

**第 1 名（0.9888）和第 4 名（0.9536）是同一组超参数（AdamW + 1e-4）的两次运行，差了 3.5 个点。**

| 目录 | mAP50 |
|:---|:---|
| `model/20260627_232146/yolov8m_AdamW_1e-4/` | **0.9888** |
| `model/20260627_155216/yolov8m_AdamW_1e-4/` | **0.9536** |

**原因分析**：

1. **验证集只有 30 张** ⇒ 单个样本翻转就能改变 **3.33 个点**（1/30）
2. 两次运行的差异（3.5 点 ≈ 1 个样本）**完全在噪声范围内**
3. 训练本身存在未记录的随机性（虽然 `seed=42` 设了，但 CUDA 非确定性算子、数据加载顺序、以及两次运行之间 `amp` 设置不同都会影响）

> **结论**：**Step4 的整个超参数排名是噪声**。"AdamW+1e-4 最优"这个结论**没有统计依据**。
>
> **但有趣的是**：最终提交的模型确实用了这个组合（`step5/best1/yolov8m_AdamW_1e-4/`），而它在 Step6 的平台实测中给出了 F1=0.37529。**这个选择是否比 SGD+5e-4 更好，从未被验证过。**
>
> **正确的做法**：至少 100~200 张验证集，或 k-fold 交叉验证。Step7 之后就达到了 320 张（单样本影响 0.31 点），但那时模型已经选定了。

**⚠️ 勘误**：`S4conclusion.md` 称 "AdamW 训练耗时约 5~6.5 小时/5 轮"（实测 6.8 小时），称 SGD+5e-4 "训练耗时极短，仅 **0.3 小时**"（实测 19 分钟 = 0.32 小时 ✅ 这个对，但同脚本跑的 SGD+1e-4 用了 63 分钟）。

**最终选择**：AdamW + 1e-4（0.9888），权重复制到 `step5/best1/yolov8m_AdamW_1e-4/train/weights/best.pt`。

**选择理由**（原文档）：推理速度与优化器无关，只在训练时体现差异，所以选精度最高的无速度风险。（这个推理本身是对的，只是"精度最高"这个前提不可靠。）

### 8.3 ⚠️⚠️ 版本混乱的 X2Paddle 产物（重要发现）

项目里存在 **5 个** `x2paddle_code.py`，分属 **两种互不相同的版本**，这正是原文档里"三个补丁"描述的来源与混乱之处。

| 文件 | 行数 | `paddle.slice` 的 starts/ends | `paddle.cast` |
|:---|:---:|:---|:---|
| `step5/tool/x2paddle_output/` | 514 | **动态**：`starts=Constant_7_cast, ends=Mul_cast` | 10 个（含 **4 个 float32 cast** + int32） |
| **`step5/tool/x2paddle_v2_output/`** | 504 | **硬编码**：`starts=[0], ends=[2]` / `starts=[2], ends=[4]` | **0 个** |
| `step6/P2/x2paddle_512/` | 491 | **硬编码**：同上 | **0 个** |
| **`step6/P2/x2paddle_512_v2/`** | 491 | **硬编码**：同上 | **0 个** |
| `step9/model/x2paddle_output/` | 514 | **动态**：`starts=Constant_7_cast, ends=Mul_cast` | 5 个（1 int64 + 4 int32，**无 float32**） |

**真实的三个补丁（修正版）**：

| # | 补丁 | 应用于 | 证据 |
|:---|:---|:---|:---|
| **1** | **MaxPool dilation 断言放宽** → `x2paddle/op_mapper/onnx2paddle/opset_legacy.py` ~L1980，允许 `dilation ∈ {None, [1], [1,1]}` | X2Paddle 源码（两个环境） | 文档记录；不可从产物直接验证，但转换能成功说明必须 |
| **2** | **int64/float32 类型提升** → 算术运算前显式 `paddle.cast(..., 'float32')` | **只在 `step5/tool/x2paddle_output/`（v1，514 行）** | 该文件 L485-488 有 4 个 float32 cast：<br>`paddle.add(x=paddle.cast(Gather, 'float32'), y=paddle.cast(Constant_8, 'float32'))`<br>`paddle.divide(x=Add, y=paddle.cast(Constant_9, 'float32'))`<br>`paddle.multiply(x=Div, y=paddle.cast(Constant_10, 'float32'))`<br>`paddle.multiply(x=Div, y=paddle.cast(Constant_11, 'float32'))` |
| **3** | **DFL Slice 索引硬编码** → `starts=[0], ends=[2]` / `starts=[2], ends=[4]` | **`x2paddle_v2_output/`、`x2paddle_512/`、`x2paddle_512_v2/`** | 这三个文件都是硬编码整数（见上表） |

**⚠️ 关键修正**：原文档把补丁 #2 和 #3 描述成"对生成的 `x2paddle_code.py` 约 L485-488 / L482-494 的修改，且在 26csresult 环境生效"。实测发现：

- **两个补丁是不同版本文件上的不同改动**，不是同一个文件的两处修改
- **`step9/model/x2paddle_output/`（Step9 的产物）既有 float32 cast 也没有硬编码 slice** —— 但它有 int32 的 slice 索引 cast，与 v1（514 行）几乎一致
- **补丁 #2（float32 cast）在 Step6 和 Step9 的所有产物里都不存在**

> **这意味着**：原文档声称"26csresult 的 X2Paddle 已打源补丁，自动生成硬编码 starts/ends"—— 但 Step9 的产物（同样是 26csresult 环境、同样 514 行版本）**生成了动态索引**。所以**"自动生成硬编码"的说法不成立**，硬编码是**手工编辑**的结果。

### 8.4 ⚠️ DFL Slice 索引问题的真实风险（比文档描述更严重）

从 `step9/model/x2paddle_output/x2paddle_code.py` 的真实代码：

```python
# L483
Shape_output_0 = paddle.cast(x=Shape_output_0, dtype='int64')
# L485-488
Add_output_0   = paddle.add(x=paddle.cast(Gather_output_0, 'float32'),
                            y=paddle.cast(Constant_8, 'float32'))
Div_output_0   = paddle.divide(x=Add_output_0, y=paddle.cast(Constant_9, 'float32'))
Mul_output_0   = paddle.multiply(x=Div_output_0, y=paddle.cast(Constant_10, 'float32'))
Mul_1_output_0 = paddle.multiply(x=Div_output_0, y=paddle.cast(Constant_11, 'float32'))
# L489-494
Constant_7_cast = paddle.cast(x=Constant_7, dtype='int32')
Mul_cast        = paddle.cast(x=Mul_output_0, dtype='int32')
Mul_cast        = paddle.cast(x=Mul_output_0, dtype='int32')       # 重复
Mul_1_cast      = paddle.cast(x=Mul_1_output_0, dtype='int32')
# L491/L494
Slice   = paddle.slice(input=dfl_Reshape_1, axes=[1],
                       starts=Constant_7_cast, ends=Mul_cast)
Slice_1 = paddle.slice(input=dfl_Reshape_1, axes=[1],
                       starts=Mul_cast, ends=Mul_1_cast)
```

其中 `Constant_6..11` 是**从 `model.pdparams` 加载的 `int64` 参数**，`Constant_14` 不在参数文件里（所以被硬编码为 `paddle.full(..., fill_value=2.0)`）。

**风险**：如果那批 `Constant_6..11` 参数在某个转换路径里缺失，`create_parameter(..., Constant(0.0), dtype='int64')` 会让 start=0 / end=0，产生**空切片**。这是一个潜在的静默失效模式。

而硬编码版（Step6 的产物）把这行变成：

```python
Slice   = paddle.slice(input=dfl_Reshape_1_output_0, axes=[1], starts=[0], ends=[2])
Slice_1 = paddle.slice(input=dfl_Reshape_1_output_0, axes=[1], starts=[2], ends=[4])
```

彻底消除了这个风险，也让模型可在 GPU 上运行。

**⚠️❗ Step9 用回了未修补的动态索引版本** —— 这直接解释了为什么 `step9/predict.py` 的 GPU 分支写的是 `enable_use_gpu(1000, 0)`（1000 MB，不是 step6 的 2000 MB）却仍然走 CPU：

```python
# step9/predict.py
try:
    paddle.device.set_device('gpu'); config.enable_use_gpu(1000,0)
except:
    paddle.device.set_device('cpu'); config.disable_gpu(); config.enable_mkldnn()
```

**结论**：**Step9 的提交包是 CPU-only 推理**。它的 FPS 会远低于 Step6 —— 而 Step9 的 `upload/submission.zip`（84.10 MB，07-05 07:23）**没有留下任何 FPS 记录**。

### 8.5 `predict.py` 设计（与官方模板的差异）

| 维度 | 官方模板 | 本项目 |
|:---|:---|:---|
| 预处理 | PaddleDetection 管线 | **自实现 YOLOv8 letterbox + BGR→RGB + /255** |
| 模型 I/O | 3 输入（image / im_shape / scale_factor） | **单输入 `[1,3,640,640]`，单输出 `[1,5,8400]`** |
| 后处理 | PaddleDetection 内置 NMS | **自实现浮点 NMS（IoU=0.45）+ 面积最大框选择** |
| GPU 策略 | 固定 GPU | **GPU 优先（2000MB, dev 0），异常自动回退 CPU** |
| PaddleDetection 依赖 | 必需 | **完全不需要** |

**关键常量**：

| 常量 | Step5 | Step6 P1 | Step6 P2~P4 | Step9 |
|:---|:---:|:---:|:---:|:---:|
| `CONF_THRESH` | 0.25 | 0.25 | 0.25 | 0.25 |
| `IOU_THRESH` | 0.45 | —（去 NMS） | —（去 NMS） | —（去 NMS） |

**letterbox 的精确实现**（全项目统一，含 Ultralytics 的 ±0.1 非对称取整技巧）：

```python
r = min(new_shape[0]/shape[1], new_shape[1]/shape[0])
new_unpad = (int(round(shape[1]*r)), int(round(shape[0]*r)))
dw = (new_shape[0]-new_unpad[0])/2 ; dh = (new_shape[1]-new_unpad[1])/2
img = cv2.resize(img, new_unpad, interpolation=cv2.INTER_LINEAR)
top, bottom = int(round(dh-0.1)), int(round(dh+0.1))     # ← ±0.1 保证 padding 总和精确
left, right = int(round(dw-0.1)), int(round(dw+0.1))
img = cv2.copyMakeBorder(..., value=(114,114,114))
```

**Step5 的 NMS（手写纯 NumPy）**：

```python
order = scores.argsort()[::-1]
while order.size > 0:
    i = order[0]; keep.append(i)
    ... 计算 box i 与 order[1:] 的 IoU ...
    order = order[np.where(iou <= iou_threshold)[0] + 1]   # +1 正确映射回去掉的首元素
```

注释说明了理由：**"纯浮点 NMS，保证坐标精度"** —— 为避免任何库 NMS 里的 int 转换破坏亚像素坐标，影响竞赛的 IoU 评分。

**后处理的三种输出形状分支**（全项目统一）：

```python
preds = output[0].transpose(1, 0)      # [1, N, 8400] → (8400, N)
if   preds.shape[1] >= 6: bbox_raw, score = preds[:, :4], preds[:, 4] * preds[:, 5]
elif preds.shape[1] == 5: bbox_raw, score = preds[:, :4], preds[:, 4]
else:                     bbox_raw, score = preds[:, :4], preds[:, 4:].max(axis=1)
```

`>= 6` 分支假设 **YOLOv5/v8 风格 `4 + 1(obj) + nc` 头**（单类即 6 列）。`== 5` 与 `else` 是防御性回退。**这就是同一段 `postprocess` 在 P1~P4 和 `step6/eval.py` 里逐字重复的原因。**

**最终选框**：

```python
areas = (x2-x1) * (y2-y1)
best  = argmax(areas)          # ⭐ 按「面积」不是「置信度」
```

> **关键设计**：赛制要求"面积最大的火焰"，所以选框依据是 `w*h` 而非 `conf`。这是与"常规检测取最高分"最本质的区别，也是 Step9"竖棍幻觉"问题的根源。

**鲁棒性设计**：

- `data_txt` 中的相对路径自动拼接 `data_txt` 所在目录（竞赛从任意 CWD 调用，这很重要）
- 单张图异常不中断全流程（累计 `errors`，只打印前 5 条，**只有全部失败才 `exit(1)`**）—— "部分成功也是成功"的策略
- 兼容旧格式 `.pdmodel` 与 PIR 格式 `.json`
- `export.py` 的 stdout UTF-8 重配置

```python
all_gt   = [[img_id, gt_box, False], ...]                       # 第三槽 = 已匹配标志
all_pred = [[img_id, box, score, -1], ...]                      # 第四槽 = 匹配到的 GT 索引
all_pred.sort(key=lambda x: x[2], reverse=True)                 # 全测试集按分数降序
for pe in all_pred:
```

### 9.4 ⚠️ 关键技术陷阱：改 IMGSZ 必须重导出模型

**不能只改 `predict.py` 里的 `IMGSZ`**！

YOLOv8 的检测头内有**硬编码的网格数 reshape**：

| IMGSZ | 网格数（输出第 3 维） | `x2paddle_code.py` 的 reshape |
|:---|:---|:---|
| 640 | 80² + 40² + 20² = **8400** | `shape=[1, 4, 16, 8400]` |
| 512 | 64² + 32² + 16² = **5376** | `shape=[1, 4, 16, 5376]` |

只改预处理尺寸会导致 `reshape` 报错 `5376 != 8400`。

**512 的重导出全流程**（`step6/P2/export_512.py`）：

```python
onnx_path = model.export(format="onnx", imgsz=512, batch=1, simplify=True, opset=12)
paddle_dir = os.path.join(os.path.dirname(onnx_path), "paddle_model_512")
x2paddle.convert.onnx2paddle(onnx_path, paddle_dir)
# 找 inference_model/，找不到就 os.walk 全树找含 model.pdmodel 或 model.json 的目录
# 然后复制该目录里【所有】文件（比 step5/export.py 的固定三件套更稳健）
```

### 9.5 P3 / P4 的实现细节

**P3 的三级回退链**：

```python
try:   # 1. GPU + TensorRT
    config = Config(pdmodel, params); config.enable_use_gpu(2000, 0)
    config.enable_tensorrt_engine(
        workspace_size=1 << 30,          # 1 GiB
        max_batch_size=1,
        min_subgraph_size=3,
        precision_mode=Config.Precision.Float32,
        use_static=True,
        use_calib_mode=False
    )
    return create_predictor(config)
except Exception: pass
try:   # 2. 纯 GPU
    config.enable_use_gpu(2000, 0); ...
    return create_predictor(config)
except Exception: pass
# 3. CPU
config.disable_gpu(); ...
```

**TRT 参数的解释**：

- **FP32**（非 FP16/INT8）避免任何量化精度损失，且**不需要校准数据**（所以 `use_calib_mode=False`）
- **`use_static=True`** 让 Paddle 把构建好的引擎缓存到模型旁边 —— **只有首次运行付引擎构建成本**，这对限时提交是必需的
- **`min_subgraph_size=3`** 避免 TRT 接管太小的子图（收益不抵开销）

> **P3 不支持 `model.json` PIR 回退** —— 三级块里全部硬编码 `Config(pdmodel, params)`。推测是因为 TRT 对 PIR 图支持有问题。

**P4 的批量累加器**（闭包实现）：

```python
def flush_batch():
    if not batch_tensors: return
    if len(batch_tensors) == 1:
        box = process_single(...)                       # 绝不发 batch=1
        add_result(batch_img_ids[0], box)
    else:
        boxes = run_batch(...)
        if boxes is None:                               # batch 失败 → 逐图回退
            for t, info, img_id in zip(...): add_result(img_id, process_single(...))
        else:
            for img_id, box in zip(batch_img_ids, boxes): add_result(img_id, box)
    batch_tensors, batch_infos, batch_img_ids = [], [], []
```

`run_batch` 做 `np.stack(batch_tensors, axis=0)`，**任何异常都返回 `None`** 作为明确的"回退单图"信号。循环结束后调用 `flush_batch()` 处理尾部余数。

**P4 与 P1~P3 的两个差异**：

1. P4 的 `preprocess` 返回**三维 CHW 张量**（不 `expand_dims`），batch 维在累加时才加；P1~P3 在 `preprocess` 里就加了
2. P4 的 TRT `max_batch_size=BATCH_SIZE`（=2）

### 10.2 ⚠️ 被遗忘的前奏：`hsv.py` 规则标注的失败

`step7/hsv.py`（8451 B，日志 `20260630_143337_hsv.log`）是 Step7 的**第一个尝试**，比自举迭代早两天。

**思路**：完全放弃学习式标注器，用**手工调优的 HSV 颜色阈值**直接生成 YOLO 标签。

**火焰颜色规则（精确）**：

```python
hsv = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)
lower = np.array([5, 80, 120])      # H=5,  S=80,  V=120
upper = np.array([30, 255, 255])    # H=30, S=255, V=255
mask = cv2.inRange(hsv, lower, upper)
```

在 OpenCV 的 HSV 约定里 **H ∈ [0,180]**（度数/2），所以 **H = 5~30 对应 10°~60°** —— 橙到黄，即火焰核心/主体而非红色尖端（红是 H < 5 或 > 175）。饱和度下限 80 与亮度下限 120 排斥发白和暗的区域。

**形态学与区域选择**：

```python
kernel = cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (5,5))
mask = cv2.morphologyEx(mask, cv2.MORPH_CLOSE, kernel)     # 闭运算桥接闪烁造成的断裂
contours, _ = cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)
max_contour = max(contours, key=cv2.contourArea)           # ⭐ 只取最大连通域
```

**8 像素外扩**（精确，注意 `bw`/`bh` 是对**已平移的** `x`/`y` 做钳制，右/下不会越界）：

```python
pad = 8
x  = max(0, x - pad)
y  = max(0, y - pad)
bw = min(w - x, bw + 2*pad)
bh = min(h - y, bh + 2*pad)
```

**运行结果（`20260630_143337_hsv.log`）**：


**❌ 这个方案失败了**：

- **2827 张全部被判定为"有火"**（0 张跳过）—— 因为 HSV 规则**没有最小面积过滤**，一个 5×5 闭运算后的孤立橙色像素就能生成合法标签
- **2927 张全部是正样本，零负样本** —— 一个只有正类的数据集

### 10.6 自举迭代两轮

**迭代流程**：

```
data{n} 训练 → model_v{n} → 对 2827 张全量推理 → pseudo_round{n}/（分 5 档阈值）
    → merge 高置信档（thr_098）进种子 → data{n+1} → 下一轮
```

**`gen.py`**（伪标签生成，分层写出）：

```python
TIERS = [("thr_099",0.99), ("thr_098",0.98), ("thr_095",0.95),
         ("thr_090",0.90), ("thr_000",0.10)]
# 推理参数：conf=0.1, iou=0.5, imgsz=640
# 每图取面积最大的框 → 归一化 (cx,cy,w,h)，**硬编码**除以 640/480
# 同时写 metadata.json：{stem: max_conf}
```

**`merge.py`**（合并规则）：

```python
split_seed = round_num * 10 + 42        # 每轮划分不同（R1→52, R2→62）
for stem, content in new_labels.items():
    if stem in merged:
        seed_c = 1.0                      # 种子置信度视为 1.0
        new_c  = float(new_conf.get(stem, 0.0))
        if new_c > seed_c:                # ⚠️ 死分支：new_c 恒 ≤ 1.0，永不成立
            merged[stem] = content
        conflicts += 1
```

> **⚠️ 死分支**：`new_c > 1.0` 永远为假（`gen.py` 的置信度上限是 1.0），所以**新标签永远无法覆盖种子**。这个 `if` 在功能上等价于注释。作者自己在 `S7计划2.md` 的陷阱清单里写了"新标签不可能超过 1.0，所以种子永远优先"—— 但代码里仍保留了这个不可能成立的分支。

**`converge.py`**（收敛判定，**图片数口径**）：

```python
prev_set / curr_set = {stem of *.txt}
new_added   = len(curr_set - prev_set)
growth_rate = new_added / len(prev_set) * 100
converged   = (new_added < 30) or (growth_rate < 2.0)     # threshold 默认 30（图片数！）
```

**⚠️ 与 Step8 的收敛定义完全不同**：Step7 是**图片数**口径（`<30` 张或 `<2%` 增长），Step8 是**框数 + IoU 匹配**口径（`≤5%`）。原文档只描述了 Step8 那一个。

```python
s = shapes[0]                       # 只处理第一个 shape —— 多框会被静默丢弃
x1,y1 = pts[0]; x2,y2 = pts[1]
xmin, xmax = min(x1,x2), max(x1,x2) # 处理 LabelMe 坐标方向可能反的问题
ymin, ymax = min(y1,y2), max(y1,y2)
cx = (xmin+xmax)/2/640; cy = (ymin+ymax)/2/480
w  = (xmax-xmin)/640;   h  = (ymax-ymin)/480
return f"0 {cx:.6f} {cy:.6f} {w:.6f} {h:.6f}"
```

**合并顺序**：`dict(seed_labels)` → fixes（覆盖 thr_000 中的同名）→ R2 标签（seed 冲突时胜出）。**seed 赢下所有冲突。**

### 11.6 ⚠️⚠️⚠️ 勘误：`--iou 0.9` 从未生效，且概念被误解

原文档（`S8conclusion.md` L84、`项目详细技术方案.md` L217）反复宣称：

> "**IoU=0.9 严格正样本匹配**，只学习高质量锚框 → 反而提升多框检测精度"

**代码证据**（`step8/tool/train.py`）：

```python
parser.add_argument("--iou", type=float, default=0.0)
...
iou_val = args.iou if args.iou > 0 else 0.7
log(f"Batch: {batch}, Epochs: {epochs}, IoU: {iou_val}")
try:
    results = model.train(
        data=..., imgsz=640, epochs=epochs, batch=batch,
        optimizer='AdamW', lr0=1e-4, momentum=0.9, weight_decay=0.0005,
        mosaic=0.0, mixup=0.0, copy_paste=0.0, patience=0,
        project=..., name='train', exist_ok=True,
        device=0, amp=False,
        iou=iou_val,                                  # ← 传给 Ultralytics
    )
except RuntimeError as e:
    if "out of memory" in str(e).lower() or "OOM" in str(e):
        log(f"OOM with batch={batch}, retrying with batch=8")
        batch = 8
        results = model.train(
            data=..., imgsz=640, epochs=HP["epochs"], batch=batch,
            ... ,
            device=0, amp=False,
            # ⚠️⚠️ 这里没有 iou=iou_val！
        )
```

**两个独立的错误**：

**错误 A：概念误解。** Ultralytics 的 `iou` 参数是 **NMS 的 IoU 阈值**（用于 `non_max_suppression`），**不是训练时的正样本匹配阈值**。后者在 YOLOv8 里是 TAL 的 `topk`/`alpha`/`beta`（或 v5 时代的 `anchor_t`）。

**所以 `--iou 0.9` 的真实效果**：

1. **训练期**：`iou` 写入 `args`，主要影响**训练过程中每个 epoch 的验证 NMS**。把 NMS IoU 从 0.7 提到 0.9 意味着**保留更多重叠框** ⇒ 验证 mAP 会**偏高**（宽松去重）
2. **推理期（`gen.py`）**：`gen.py` 里**硬编码了 `iou=0.5`**，与训练时的 `iou` 无关
3. **多框能力的真正来源**：是 **R5 前引入的 339 张人工多框标注 + 多框图 ×2 过采样**，不是 `--iou 0.9`

**旁证**：Phase 2 的验证 mAP50 在 0.94~0.98 之间（比 Phase 1 的 0.993~0.995 **更低**），而 Phase 3（文档说 IoU=0.7）又回到 0.980~0.983。如果 `iou=0.9` 真的提升精度，Phase 1（0.7）应该更低才对。**mAP50 的波动更可能只是过采样改变了训练分布。**

**错误 B：OOM 分支漏传参数 ⇒ 实际上 `--iou 0.9` 从未生效。**

**日志证据**：`step8/log/` 里**所有轮次**的 train 日志都写着 `Batch used: 8`（不是默认的 16）：

```
20260703_144603_train.log: Batch used: 8    ← R1
20260703_151057_train.log: Batch used: 8    ← R2
...（全部 12 个 train 日志都是 8）
20260704_215212_train.log: Batch used: 8    ← R15
```

**`Batch used: 8` 意味着每一轮都走了 OOM 重试分支** ⇒ **每一轮的 `iou` 都静默回退到 0.7**。

> **⚠️⚠️⚠️ 最终结论：Step8 全部 15 轮的 `--iou 0.9` 从未生效过。**
>
> 原文档中"Phase 2 用 IoU=0.9，Phase 3 切回 IoU=0.7"的对比实验，**在代码层面等价于同一个配置**。这个对比实验在方法学上**不成立**。
>
> 另外 OOM 分支还把 `epochs` 重置成了 `HP["epochs"]`（20），忽略 `--epochs` 参数。

### 12.5 ⭐⭐ 核心发现："竖棍形幻觉框"与三级降级算法

这是**整个项目中最重要的一个算法发现**，也是**原文档几乎完全没有记录**的部分。

#### 现象

多框模型在部分图片上会输出**细高条状（竖棍形）的幻觉框**（`h/w` 极大），且这种框**面积常常是最大的**。由于赛制要求"面积最大的火焰"，这些幻觉框会被选中并严重拉低 F1。

#### 诊断证据（`step9/tool/debug_stick.py`）

```python
print(f"Total: {len(img_paths)}, stick final boxes: {len(stick_issues)} (was 196)")
#                                                                    ↑ 修复前有 196 张
```

**修复前有 196 张图的最终输出框是竖棍形**（196/2827 = **6.9%**）。

`debug_stick.py` 的诊断元数据设计：

```python
debug = f"total={len(boxes)} max_area={...:.0f} r={h/w:.2f} c={conf:.3f}"
# reason 标签：OK | FOUND_hi | FOUND_lo | BEST_of_sticks | FALLBACK_2nd | ONLY_one
# 并按 ratio 分桶统计：(3,4] (4,6] (6,10] (10,20] (20,∞)
```

#### 修复算法（`step9/predict.py` 与 `visualize.py` 共享）

```python
STICK_RATIO_3X = 3.0   # h/w > 3  视为竖棍，触发降级
STICK_RATIO_6X = 6.0   # h/w > 6  视为极端，强制抛弃

def is_stick(b, threshold=STICK_RATIO_3X):
    """判断框是否为竖棍（高 > threshold * 宽）"""
    w, h = b['w'], b['h']
    return (h / w) > threshold if w > 0 else True      # w<=0 也视为竖棍

def select_box_with_stick_handling(boxes, conf_thresh=0.25):
    if not boxes:
        return None
    sorted_boxes = sorted(boxes, key=lambda b: b['w'] * b['h'], reverse=True)
    max_box = sorted_boxes[0]

    # ① 最大框不是竖棍 → 直接返回（绝大多数情况）
    if not is_stick(max_box, STICK_RATIO_3X):
        return max_box

    # ② 降级第 1 轮：在余下框中找「高置信度 + 非竖棍」
    for b in sorted_boxes[1:]:
        if b['conf'] >= conf_thresh and not is_stick(b, STICK_RATIO_3X):
            return b

    # ③ 降级第 2 轮：放宽置信度，任意非竖棍
    for b in sorted_boxes[1:]:
        if not is_stick(b, STICK_RATIO_3X):
            return b

    # ④ 降级第 3 轮：全是竖棍 → 选比例最不极端的
    best, best_ratio = max_box, max_box['h']/max_box['w'] if max_box['w']>0 else 999
    for b in sorted_boxes[1:]:
        r = b['h'] / b['w'] if b['w'] > 0 else 999
        if r < best_ratio:
            best_ratio, best = r, b
    if best_ratio <= STICK_RATIO_6X:
        return best
    if len(sorted_boxes) >= 2:
        return sorted_boxes[1]      # 彻底放弃最大框，取面积第二大
    return max_box                  # 只有一个框，无从选择
```

#### 算法思想

把"面积 argmax"升级为**带形状先验（shape prior）的面积 argmax**——先验是"火焰不应是细高条"。三级降级保证**永远有输出**（不会因过滤而空 `result`）。

**这是"面积最大"这一赛制规则被模型利用（reward hacking）的典型表现**：模型发现"输出一个细长的框"能最大化面积，从而抢占输出位。**单框模型比多框模型更容易拿高分，正是因为单框模型没学会这个技巧。**

`step9/log/` 目录**为空**。`debug_stick.py` 的输出格式是 `was 196`，但**修复后剩余多少张没有任何记录**。`bench_fps.py`（对比 Step7 `model_v4` 与 Step9 `model_v12` 的 CPU FPS）同样无日志产出。

按"发现顺序 + 影响面"整理，这是本复盘最有价值的部分。

### T1. 加权采样被 basename 冲突静默丢弃（Step3）★★★

- **现象**：5383 行清单 → 只有 **1558** 张唯一图片，`thr_095×3` 加权完全失效
- **代码**：`dst_img = os.path.join(YOLO_TRAIN_IMG, os.path.basename(img_path))` + `if not os.path.exists(dst_img)`
- **磁盘证据**：`yolo_dataset/train/images` = 1558 = 70 + 1488（`thr_080 ⊇ thr_095` 的并集）
- **修复**：`train1_1.py` 用 `f"{base}_{idx:05d}{ext}"` 唯一命名 + `shutil.rmtree` 干净重建 + 换新目录名
- **验证**：`yolo_dataset_fixed/train/images` = **5383** ✅
- **收益**：mAP50 0.8766 → 0.8886（+1.2 点）
- **教训**：**任何"数据加权/过采样"必须落成物理文件**。清单里的重复行会被任何按文件去重的加载器吞掉，而且**静默无警告**。

### T2. X2Paddle DFL Slice 导致 GPU 输出全零（Step5/Step6）★★★

- **现象**：同一模型 CPU 推理正常，**GPU 推理输出全零**
- **根因**：X2Paddle 生成的 DFL 切片用动态索引（`Constant_7_cast` / `Mul_cast`），在 GPU 上求值为非法值（`end=0, start=4`）
- **修复**：因输出固定 `[1,4,8400]`/`[1,4,5376]`，**硬编码** `starts=[0], ends=[2]` / `starts=[2], ends=[4]`
- **⚠️ 未推广**：**Step9 的产物没有应用这个修复** ⇒ Step9 提交包是 CPU-only（FPS 会远低于 20）
- **教训**：**跨框架转换后必须 CPU/GPU 双向验证**。只测 CPU 会漏掉这类 bug；而且**修复必须记录成清单**，否则后续步骤会重犯

### T3. X2Paddle MaxPool dilation 断言过严（Step5）

- **现象**：转换直接失败
- **根因**：YOLOv8 SPPF 使用 `MaxPool(dilation=[1,1])`，X2Paddle 只允许 `dilation=None`
- **修复**：修改 `x2paddle/op_mapper/onnx2paddle/opset_legacy.py` ~L1980，放宽断言
- **⚠️ 两个 conda 环境都要打；重装 X2Paddle 会丢失**

### T4. Paddle 3.x int64/float32 类型不兼容（Step5）

- **现象**：转换后代码在 Paddle 3.x 下算术运算报错
- **修复**：在 `add`/`divide`/`multiply` 前显式 `cast(..., 'float32')`（**只在 v1 产物里，`_v2` 中已移除**）

### T5. PIR `.json` 格式在 Paddle 2.6.2 上 segfault（Step6）★★

- **现象**：`copy_to_cpu()` 时进程崩溃
- **根因**：`26cnsoft`（Paddle 3.3.1）的 X2Paddle 输出 PIR `.json` 格式，Paddle 2.6.2 推理引擎不兼容
- **修复**：**必须用 `26csresult` 的 X2Paddle 转换**，产出旧格式 `.pdmodel`
- **产物对照**：`x2paddle_512/`（废弃）vs `x2paddle_512_v2/`（可用）
- **教训**：**转换环境必须匹配推理环境的 Paddle 版本**

### T6. 改 IMGSZ 必须重导出模型（Step6）★★★

- **现象**：把 `IMGSZ` 从 640 改成 512 后 `reshape` 报错 `5376 != 8400`
- **根因**：检测头内网格数硬编码（640→8400，512→5376）
- **修复**：`export(format="onnx", imgsz=512, opset=12)` + 重跑 X2Paddle + `convert_model.py` 重新 `paddle.jit.save`
- **验证**：`paddle.slice` 的 `reshape(shape=[1,4,16,5376])` 与 `model/predict.py` 的 `IMGSZ=512` 一致

### T7. AdamW `momentum=None` 导致训练异常（Step4）★★

- **代码**：`momentum=0.937 if opt=='SGD' else None`
- **现象**：日志反复出现 `⚠️ yolov8m_AdamW_1e-4 未生成best.pt`，跑了 6.8 小时看似白跑
- **真相**：权重其实生成了（`test.py` 找到了），是**脚本的路径判断有误**（`save_dir/weights/` vs `save_dir/train/weights/`）
- **修复**：`train1_1.py` → `momentum_val = 0.937 if opt == 'SGD' else 0.9`
- **教训**：① Ultralytics 的 `momentum` 对 AdamW 也有语义（映射到 beta1），不能留空；② **"文件没生成"要先怀疑检查路径，而不是训练失败**

### T8. Windows 下 YOLO `train.txt` 列表式配置失效（Step7）★★

- **现象**：`train: 892 images, 0 backgrounds`（应为 892 张都有标签），`cls_loss=237.6`
- **根因**：`os.sep`（`\`）与 YOLO 期望的路径分隔符不匹配
- **修复**：改用**目录格式**（`train: train` / `val: val`），依赖 YOLO 内部的 `\images\` → `\labels\` 字符串替换
- **注意**：替换机制要求路径中**完整包含 `\images\`**

### T9. AMP check 反复下载模型卡住（Step7）

- **现象**：训练启动时反复 curl 超时下载 `yolo26n.pt`，每次约 3 分钟
- **修复**：`amp=False` 跳过 AMP 检查
- **副作用**：`amp=False` 只在 `step4/train1_1.py` / `step7` / `step8` 出现，Step3 与 Step4 首版是默认 AMP 开 ⇒ **它们的数值表现不可直接比较**

### T10. 硬链接跨卷失败 / 硬链接导致 val 为空（Step7/Step8）

- **现象 A**：`os.link` 跨分区抛 `OSError`
- **现象 B**：`dataN/val` 为空，YOLO 报 "No images found in val"
- **修复**：统一封装 `hardlink_or_copy(src, dst)`，`except (OSError, NotImplementedError)` 时回退 `shutil.copy2`
- **⚠️ 唯一例外**：`step8/tool/init.py` 的 `data1/images` 用的是 `copy2`（这里正是 T10-B 的现场）

### T11. 僵尸 python 进程累积拖慢训练（Step8）★★

- **现象**：物理内存 28/32 GB，训练从 0.3 s/batch 恶化到 **30 s/batch**（100 倍）
- **修复**：定期 `taskkill` 清理残留 `python.exe`，检查 `nvidia-smi`
- **教训**：**长跑训练前先检查系统资源**，"训练突然变慢 100 倍"通常是环境问题不是模型问题

### T12. OOM 重试分支漏传参数（Step8）★★★

- **代码**：主路径传了 `iou=iou_val`，**OOM 重试路径没传**，且把 `epochs` 重置成 `HP["epochs"]`
- **日志证据**：**所有 12 个 train 日志都写 `Batch used: 8`** ⇒ 每轮都走了 OOM 分支 ⇒ **`--iou 0.9` 从未生效**
- **后果**：原文档基于"Phase 2 = IoU 0.9 vs Phase 3 = IoU 0.7"的整个对比实验**在方法学上不成立**
- **教训**：**异常/重试分支必须传齐所有参数**。否则参数会**静默回退默认值**，产生无法从日志发现的错误结论

### T13. Resume 失败（Step8）

- **现象**：恢复 checkpoint 时 CUDA OOM
- **修复**：**不 resume**，直接用 `last.pt` 作为 `weights` 参数重新训练
- **⚠️ 且 `resume=True` 时 `project`/`name`/`epochs` 参数都是 no-op**（Ultralytics 从 checkpoint 恢复原始参数）

### T14. 过采样命名冲突（Step8）★★

- **现象**：`_r` 后缀文件被反复追加（`_r2`、`_r10`、`_r11`、`_r12`）
- **根因**：重跑过采样时没有清空输出目录，计数器从上次状态继续
- **后果**：`data10/train/images` 膨胀到 **7240 张**（其他轮 ~2180），该轮训练分布与其他轮不可比
- **⚠️ 声称的修复（`defaultdict(int)`）在任何现存脚本里都不存在** —— 因为生成脚本本身丢失了
- **建议修复**：用 `defaultdict(int)` 严格从 0 计数，并在 rebuild 开始时 `shutil.rmtree(out_dir)`

### T15. LabelMe JSON 坐标方向不定（Step7/Step8）

- **现象**：`points: [[x1,y1],[x2,y2]]` 中可能 `x1 > x2`
- **修复**：`xmin, xmax = min(x1,x2), max(x1,x2)`（`build4.py` / `rebuild.py` 均已处理）

### T16. `build4.py` 只取 `shapes[0]`（Step7）

- **代码**：`s = shapes[0]`
- **后果**：一图多框时**第二个之后的框被静默丢弃**
- **对比**：Step8 的 `rebuild.py` 遍历**所有** `shapes` ✅
- **未暴露原因**：9 张人工修正样本恰好都是单框

### T17. `cv2.imread` 无法读中文路径（7.19 演示工程）★

- **现象**：读取 `E:\desktop\school\26中国软件杯\...` 下的图片失败
- **修复**：`np.frombuffer(open(p,'rb').read(), np.uint8)` + `cv2.imdecode(..., cv2.IMREAD_COLOR)`

### T18. 本地 GPU 完全不可用（贯穿全程）★★★

- **现象**：Paddle 2.6.2（CUDA 11.8 runtime）不支持 RTX 5060 Ti（CC 12.0），GPU 推理输出全零或 segfault
- **影响**：**本地无法测速**，FPS 只能靠平台反馈
- **后果**：Step7 的"预估 FPS 35–45"从未被验证，直接影响了后续路线决策

### T19. `sample100` 不代表平台分布（Step6）★★★

- **现象**：本地 F1 0.9749 vs 平台 F1 0.37529（差 2.6 倍）
- **影响**：本地只能做**功能验证**，精度判断必须依赖平台
- **教训**：**本地验证集必须与评测集同分布**。这是本项目最大的评估方法论失误

### T20. 竖棍形幻觉框（Step9）★★★

- **现象**：**196 张图（6.9%）** 的"面积最大框"是极细高的幻觉框
- **修复**：三级降级的形状先验算法（见 12.5）
- **⚠️ 修复效果无法量化**：`step9/log/` 为空，只剩 `was 196` 这一个数字
- **教训**：**"面积最大"这个规则本身有漏洞** —— 面积大不等于目标大。多框模型容易被细长背景纹理骗到（**reward hacking**）

### T21. 收敛判定与训练时序错位（Step8）★★

- **现象**：R9/R10/R13 的 `converge.py` 时间戳**早于**对应训练日志；部分轮次只有 gen 没有 train
- **后果**：`converge.py` 比较的是"上一轮模型的输出"，收敛曲线与训练曲线不同步
- **教训**：自动化流水线必须保证"训练完成 → 推理 → 收敛判定 → 合并"的**严格串行**，且日志时间戳可验证

### T22. 验证集泄漏（Step8）★★★

- **现象**：`data12` 的 `train ∩ val = 264` 张，另有 96 张 val 在 train 里有 `_r2` 孪生
- **根因**：train 是从过采样/欠采样规则**组装**的，不是作为 val 的**补集**算出来的
- **后果**：**验证 mAP50 虚高**，直接解释了为什么 0.94~0.98 的验证分数没有实用收益
- **对照**：`step7/data4` 没有重叠（一次 shuffle 后的不相交切片）✅

### T23. `build.py` 的字典序排序 bug（Step8）

- **代码**：`last_round = sorted(STEP8.glob("pseudo_round*"))[-1]`
- **问题**：字典序下 `pseudo_round9` > `pseudo_round15`。在 ≥10 轮时"最后一轮"会选错
- **当前是否触发**：`build.py` 在 R4 时运行（那时只有 `pseudo_round1~4`），所以**未触发**，但是潜在 bug
- **修复**：用 `max(..., key=lambda p: int(p.name.replace("pseudo_round","")))`

### T24. 三个"被记录但完全无效"的实验（Step2）★★★

- **`Exp-D2_weighted`**：`_current_weights` 全局变量从未被赋值 → 加权损失 = 无权损失
- **`Exp2-B`（标签平滑 0.1）**：`label_smoothing` 从未传给损失函数
- **`Exp2-E`（伪标签权重衰减）**：`pseudo_w` 只被插值进日志字符串，从不乘任何损失
- **后果**：`S2conclusion.md` 的结论 F3"标签平滑有害"**完全没有依据**；"Exp2-E 同模式"是同义反复
- **教训**：**"配置存在" ≠ "配置生效"**。跑消融前必须验证每个变量真的改变了行为（例如打一行 `assert weights is not None`）

### T25. `annotate.py` 的置信度统计是死胡同（Step1）

- **现象**：`annotate.py` 输出详尽的置信度直方图（0.01 步长、7 个阈值档位）
- **但**：`gen_labels.py` 用的阈值 `[0.99,0.95,0.90,0.80,0.75]` 是**硬编码**的，与这份统计无关
- **教训**：**统计产出了就要消费它**，否则是纯粹的计算浪费

### T26. `split.json` 与 `real_val.txt` 两套验证集（Step2）★★

- **现象**：Step2 用 20 张随机（`split.json`），Step3/4 用 30 张时序（`real_val.txt`）
- **后果**：Step2 的 F1 与 Step3/4 的 mAP50 **不可比**，跨框架的"前后对比"被混淆
- **教训**：**验证集必须一次定义、全局唯一**

### T27. F1 评估跨图匹配（Step1/Step2）★★★

- **代码**：`train2.py` / `eval.py` / `train_exp.py` / `train_exp2.py` 的 `evaluate_f1()` 把整个验证集的 GT 和预测池化，**不绑 image id**
- **后果**：A 图的预测可以匹配 B 图的真值 ⇒ TP/FP 计数任意膨胀/收缩
- **对照**：`step6/eval.py` **做对了**（`if ge[0] != pe[0]: continue`）
- **教训**：**评估代码比训练代码更需要 review**。一个"看起来合理"的贪心匹配可能是完全错误的

## 十七、复盘：做对了什么、做错了什么、如果重来

### 17.1 做对了什么

**① 工程规范先行（最大亮点）**

`rule.txt` 的三条规则（简短命名 / 强制日志 / 数据隔离）在整个 9 步约 70 个脚本中被大体严格执行。效果：

- **数据隔离**让每个 step 可以独立重跑，不会污染上游（`step7/data4` 只硬链接 `captures`，从不改 `step2/final_data`）
- **日志规范**让每一步的 mAP/数量/时间都可追溯——**本文档的绝大部分"实测数据"都来自这些日志**。这也是为什么原文档的错误能被发现
- **`code/` 目录留档**（数据集构建时复制当轮脚本快照）保证了可复现性（`data1`~`data6` 都有）

> **反面印证**：Step9 完全没写日志，结果它的所有关键结果（竖棍修复效果、本地 F1、CPU FPS）**永不可知**；Step8 丢失了过采样脚本，导致 `data9`~`data15` **无法复现**。

**② 用"一次推理 + 离线调阈值"解耦了实验维度**

`step2/infer.py` 把 2827 张的原始检测结果序列化成 pkl，之后 `gen_labels.py` 可以零成本尝试 5 个阈值。这个设计把"一次 GPU 推理（分钟级）"与"多组阈值实验（秒级）"解耦，是后续所有配方探索的效率基础。

**③ 验证集划分的时序意识**

识别出"`sample100` 是视频连续抽帧，随机划分会虚高"，改为**时序均匀抽取**（`np.linspace(0,99,30)`）。这是正确的数据科学判断。（虽然 30 张仍然太小，但方向对了。）Step8 进一步推广到全量 2827 张的时序划分（`[0::6]`）。

**④ 敢于否定自己的结论**

Step2 得出"Epoch 1 即最优"后，Step3 直接改用 **3 epoch**、Step4 用 **5 epoch** —— 把 Step2 的发现落地成了计算量的巨大节省（对比 Step1 的 200 epoch）。

**⑤ 快速试错、独立文件、可回退**

Step6 的 P1/P2/P3/P4 四版本独立目录；Step9 的 `fix_bbox.py` → `fix_bbox2.py` → `fix_bbox3.py` 三版迭代（**19:08 → 19:11，3 分钟一版**）；Step8 的三级 tracing 级联（`convert_model.py`）。都体现了高效的工程节奏。

**⑥ 发现并解决了"竖棍形幻觉框"（最有价值的单项发现）**

这是一个**原始文档完全没记录的算法发现**。它本质上是"面积最大"这条赛制规则被模型利用（reward hacking）的典型案例，也是多框模型反而不如单框模型的原因。

**⑦ 打通了完整的跨框架链路**

PyTorch → ONNX → X2Paddle → Paddle 静态图，含 3 个必须的 X2Paddle 补丁、双 conda 环境分工、DLL 手工部署。这条链路本身就是可复用的工程资产。

### 17.2 做错了什么（按严重程度排序）

#### ❌ 错误 1（最致命）：评估方法论与数据质量策略同时失效

**问题 A：验证集与评测集分布不一致**

- 本地用 `sample100` 验证得到 F1 0.9749，平台 0.37529（**差 2.6 倍**）
- 更糟的是：**`sample100` 的伪标签就是由在 `sample100` 上训练的模型生成的** ⇒ 本地验证是在"用模型自己的输出验证模型自己"
- **没有任何一步做过"验证集图片从未参与伪标签生成"的检查**

**问题 B：训练集 98.7% 是伪标签**

- 5313 / 5383，只有 70 张真实监督
- 伪标签由**只有 100 张真实标注训练出的 Faster R-CNN**生成，且每图只取最大框
- 结果是模型学到了"输出画面中最大最亮的区域"这个捷径

**问题 C：验证集长期过小，所有调参结论都不可靠**

| 阶段 | 验证集 | 单样本影响 mAP |
|:---|:---:|:---|
| Step1 | 20 张 | **5.0 点** |
| Step2 | 20 张 | **5.0 点** |
| Step3/4 | 30 张 | **3.3 点** |
| Step7 | 191 / 320 张 | 0.3~0.5 点 |
| Step8 | 472 张（**但有泄漏**） | 0.2 点 |

**Step4 的"AdamW+1e-4 最优（0.9888）"与同参数重跑（0.9536）差 3.5 点 = 1 个样本** ⇒ **Step4 的整个超参数排名是噪声**。

**正确做法**：

1. 把 100 张真实标注**永久固定**划为 70 训练 / 30 验证，**验证集不参与任何伪标签生成与训练**
2. 或引入与评测集同分布的外部数据做验证
3. 监控"伪标签与真实标注的一致性"（在 30 张真实集上评估伪标签本身的 F1）
4. **至少 100~200 张验证集**，或用 k-fold 交叉验证

#### ❌ 错误 2：在失去平台锚点后继续投入 40 小时精度探索

Step6 暴露了"本地指标不可信"这个教训，**但 Step7/8/9 都违反了这个刚学到的教训**：

- Step7 完成转换后**没有提交**，只留下"预估 FPS 35–45"（未验证）
- Step8 投入 15 轮训练（约 30 小时 GPU），**从未提交**
- Step9 完成打包（07-05 07:23），**从未提交**

**而这 40 小时全部建立在一个未验证的推断之上**（"IMGSZ=640 会导致 FPS 不合格"）。

**正确做法**：**每一步转换完成后立即提交一次平台**。提交成本只是一次压缩上传（几分钟），能拿到真实的 FPS 和 F1。这比 40 小时盲跑便宜几个数量级。

**从物理推算看这个推断其实站不住**：Step5（640 + NMS）是 14.35 FPS，而 Step6 的 P1 vs 基线的本地 FPS 是 7.10 vs 约 7.4 —— **NMS 几乎不耗时**。所以 640 + 去 NMS 的平台 FPS 很可能在 14~18 之间（危险但未必一定低于 20）。**一次提交就能回答的问题，被推断代替了。**

#### ❌ 错误 3：Step8 的方法学全面失效（产出不可信）

| 问题 | 后果 |
|:---|:---|
| `--iou 0.9` 从未生效（OOM 重试漏传参数） | **Phase 2 vs Phase 3 的核心对比实验不成立** |
| train ∩ val = 264（验证集泄漏） | 验证 mAP50 虚高 |
| `data10` 过采样累积失控（7240 张） | 该轮训练分布与其他轮不可比 |
| 950 个标签未进入任何 split | 数据浪费 |
| R9/R10/R13 无训练日志；converge 与 train 时序错位 | 15 轮的连续性无法验证 |
| 生成脚本丢失 | `data9`~`data15` 无法复现 |

**唯一有价值的产出**：339 张人工多框标注 → `labelme_dataset12`（3713 框）。**但这也说明：人工标注的边际收益远高于自举迭代。**

#### ❌ 错误 4：三个实验"配置存在但完全无效"（Step2）

`Exp-D2_weighted`（加权损失）、`Exp2-B`（标签平滑）、`Exp2-E`（权重衰减）**都没有实际生效**。而 `S2conclusion.md` 的结论 F3（"标签平滑有害"）正是基于 `Exp2-B` 与 `Exp2-A` 的比较 —— 而它们是同一个实验。

**正确做法**：跑消融前，对每个变量加一行运行时断言（如 `assert weights is not None`），或至少在日志里打印"该变量的实际生效值"。

#### ❌ 错误 5：Step9 提交包是 CPU-only（技术债未跨步传递）

补丁 #3（DFL Slice 硬编码）在 Step6 被手工应用并**验证有效**（GPU FPS 58.28），但**Step9 重新转换时没有应用**，导致 Step9 的模型 GPU 推理失败、只能 CPU 运行（本地 FPS 10.81 < 20 门槛）。

**正确做法**：把补丁做成**可执行的后处理脚本**（`postprocess_x2paddle.py`），而不是手工编辑。或者把"GPU 输出全零"做成一个验收测试。

#### ❌ 错误 6：F1 评估跨图匹配（Step1/Step2）

`evaluate_f1()` 把整个验证集的 GT 和预测池化后匹配，**没有绑定 image id**，导致 A 图的预测可以匹配 B 图的真值。**Step1/Step2 的所有 F1 数字都因此不可信。**

**讽刺的是**：同一个作者在 `step6/eval.py` 里把这件事做对了（`if ge[0] != pe[0]: continue`）。这说明问题不是能力，而是**评估代码没有被 review**。

#### ❌ 错误 7：A 榜 `infer_cfg.yml` 的 `label_list` 未替换

80 个 COCO 类名躺在提交包里。虽然没出问题（`predict.py` 不读它），但**这是一个纯粹的运气**。

**正确做法**：导出后**逐字段核对 `infer_cfg.yml`**（`label_list`、`draw_threshold`、`Preprocess`），写成 checklist。

#### ❌ 错误 8：Step9 完全没有日志

`s9/tool/` 下 6 个脚本（`export.py` / `eval.py` / `visualize.py` / `pack.py` / `debug_stick.py` / `bench_fps.py`）**都没写日志**，直接违反项目自己的规则 2。导致：

- 竖棍修复后到底剩多少张？**不知道**（只有 `was 196`）
- Step9 的本地 F1？**不知道**
- 全量可视化检出多少候选框？**不知道**
- Step9 的 CPU FPS？**不知道**

#### ❌ 错误 9：`build4.py` 的 `json_to_yolo()` 只取 `shapes[0]`

一图多框时，第二个之后的框被静默丢弃。9 张人工修正样本恰好都是单框，所以没暴露。

#### ❌ 错误 10：大量硬编码绝对路径（归档后全部失效）

所有脚本硬编码 `E:\desktop\traintoolB\...`，而项目实际被整理到 `E:\desktop\school\26中国软件杯\traintoolB\...`。**任何脚本现在都无法直接运行**（运行会创建一个平行目录树）。

唯一例外：`sample100/view.py`（全部相对 CWD）。

**正确做法**：用 `pathlib.Path(__file__).resolve().parents[N]`，或环境变量 / 配置文件。

### 17.3 如果重来做（一个具体的替代方案）

#### 阶段 0：评估基础设施（Day 1–2）

1. 把 100 张真实标注**永久固定**划分为 70 训练 / 30 验证，验证集**不参与任何伪标签生成与训练**
2. 建立"提交模拟器"：本地实现完整的 **F1@IoU0.5** 计算（image-scoped 贪心匹配，参考 `step6/eval.py`）+ 逐张 TP/FP/FN 明细输出
3. **明确原则：每次关键决策前必须有一次平台提交作为依据**（提交成本远低于盲猜）

#### 阶段 1：先解决合规，再谈精度（Day 3–4）

4. 直接用 **YOLOv8n/s**（3M / 11M 参数）在 100 张真实标注上训练 baseline
5. 先跑通 **PyTorch → ONNX → X2Paddle → Paddle → 提交** 全链路
6. 拿到**真实的平台 FPS 与 F1**。这一步能在 2 天内回答"小模型够不够快、精度天花板在哪"

> 这一步会避免 Step1/Step2 用 Faster R-CNN 做教师模型的巨大浪费 —— **如果一开始就知道 FPS 门槛是硬约束，就不该用 ResNet-50-FPN 做伪标签器**。

#### 阶段 2：数据质量（而不是数据数量）（Day 5–10）

7. 伪标签策略改为：**只在置信度 ≥0.9 且多模型一致的图片上生成**。例如 YOLOv8m + YOLO11m 交叉验证，只有两模型 IoU ≥0.7 的区域才作伪标签（**多模型投票去噪**）
8. 保留 **20~30% 的真实标注图片完全不参与伪标签**，作为"伪标签质量探针"
9. **把算力预算的 30% 投入到人工标注上** —— Step8 的 339 张人工多框标注带来了最明显的（也是唯一可信的）能力提升
10. **不要在单框模型上做多框自举** —— 单框模型的输出分布天然抑制多框，Step8 的 Phase 1 已经证明了这一点（4 轮只从 35 张双框图涨到 111 张）

#### 阶段 3：模型与推理（Day 11–14）

11. 用 **400~800 张验证集**做超参搜索（Step8 后期的 472 张是合理量级），或 k-fold 交叉验证
12. 推理后处理加入**形状先验**（竖棍过滤）—— 这个发现应该在 Step5 就做，而不是 Step9
13. 如果想恢复 640 精度，考虑**换更小的模型**（YOLOv8s @ 640 的 FLOPs ≈ YOLOv8m @ 512）而不是降分辨率
14. **把 X2Paddle 补丁做成可执行脚本 + 加 GPU 输出验收测试**

#### 阶段 4：工程收尾

15. 所有路径改为相对路径 + 配置文件
16. 每个脚本强制日志（含耗时、数量、关键指标）—— **尤其是评估脚本**
17. `infer_cfg.yml` 逐字段核对 checklist
18. 消融实验的每个变量加运行时断言

### 17.4 可直接复用的经验清单

| # | 经验 | 适用场景 |
|:---|:---|:---|
| 1 | **加权采样必须物理化**：清单里的重复行会被按文件去重的加载器静默吞掉，要复制文件并唯一命名 | 任何"数据加权/过采样"需求 |
| 2 | **跨框架转换后必须 CPU + GPU 双向验证** | PyTorch→Paddle / →ONNX / →TRT |
| 3 | **PIR `.json` 与旧 `.pdmodel` 不通用**：转换环境要匹配推理环境的 Paddle 版本 | Paddle 2.x vs 3.x |
| 4 | **改输入尺寸 = 必须重导出模型**（检测头网格数硬编码） | 任何 grid-based 检测器 |
| 5 | **异常/重试分支必须传齐所有参数**，否则参数静默回退默认值 | 所有带 OOM/异常重试的训练脚本 |
| 6 | **验证集必须 ≥100 张，且最好与被评测集同分布** | 一切模型选择 |
| 7 | **本地指标只能做功能验证，不能做精度判断**（若分布不同） | 竞赛/私有评测集场景 |
| 8 | **每次关键决策前先拿一次真实平台反馈** | 有提交机会时 |
| 9 | **评估代码比训练代码更需要 review**：匹配逻辑必须绑定 image id | 所有检测/检索评估 |
| 10 | **"配置存在" ≠ "配置生效"**：消融实验每个变量加运行时断言 | 任何消融/超参搜索 |
| 11 | **"面积最大"这类规则要配形状/语义先验**，否则模型会 reward hack | 单目标选择类后处理 |
| 12 | **Windows 下 YOLO 用目录格式（`train: train`），不用 `train.txt`** | Windows + Ultralytics |
| 13 | **`amp=False` 可避免 AMP check 下载模型造成的启动卡顿**，但会让结果与其他配置不可比 | 离线/网络受限环境 |
| 14 | **`cv2.imread` 不支持中文路径**，用 `np.frombuffer` + `cv2.imdecode` | Windows 中文路径 |
| 15 | **收敛判定流水线要严格串行**：训练完成 → 推理 → 判定 → 合并，且日志时间戳可验证 | 自举/迭代式训练 |
| 16 | **规则方法（HSV 等）需要面积/形状先验和负样本约束**，否则会把整个数据集标成正样本 | 传统 CV 标注方案 |
| 17 | **过采样时用 `defaultdict(int)` 严格计数，并在 rebuild 前清空输出目录** | 多次迭代的数据集构建 |
| 18 | **长跑训练前先检查系统资源**（僵尸进程会让训练慢 100 倍） | 多轮连续训练 |
| 19 | **不要用 `resume=True` 改超参**（Ultralytics 会从 checkpoint 恢复全部原始参数） | Ultralytics |
| 20 | **数据集划分要用补集而非独立组装**，否则会产生 train/val 重叠 | 任何带采样的数据划分 |

## 附录 C：一句话结论

> **A 榜**：在 PaddleDetection 原生框架上用 PP-YOLOE+ CRN-S 完成 3 类检测，**F1 0.85396 / FPS 22.6**，两项均达标，是干净利落的一次交付。（唯一隐患：`infer_cfg.yml` 的 `label_list` 忘了从 80 类 COCO 换成 3 类，靠 `predict.py` 不读它而侥幸没事。）

> **B 榜**：在只有 100 张真实标注的极端条件下，**用 torchvision Faster R-CNN（ResNet50-FPN-v2）做教师模型生成伪标签**（注意：不是 YOLO），再把数据扩到 5383 / 2139 个样本训练 YOLOv8m；打通了 **PyTorch → ONNX → X2Paddle → Paddle 静态图** 的完整链路（含 3 个必须的 X2Paddle 补丁、双 conda 环境分工）；并用**"去 NMS + 面积 argmax + 降分辨率到 512"** 把 FPS 从 14.35 提升到 **58.28（+306%）**，跑通了硬门槛。

> **但最终 F1 只有 0.37529**。根因是**训练集 98.7% 是伪标签**（且每图只取最大框，模型学到的是"输出画面中最大最亮的区域"这个捷径），加上**本地验证集 `sample100` 与平台测试集分布不一致**（更糟的是 `sample100` 的伪标签正是由在它上面训练的模型生成的），导致所有本地指标（0.97+）都失去了判别力。

> **最大的教训**：**在竞赛/私有评测集场景中，本地指标的价值完全取决于分布一致性。没有同分布验证集时，每一次关键决策都必须用一次真实平台提交来锚定。** 本项目在 Step6 之后就失去了这个锚——Step7/8/9 三轮精度探索（共约 40 小时 GPU 时间）全部建立在"IMGSZ=640 会导致 FPS 不合格"这个**未验证的推断**之上（而从 Step6 的数据看，NMS 几乎不耗时，所以 640 的 FPS 未必低于 20）。

> **最严重的隐藏缺陷**：Step8 全部 15 轮的 `--iou 0.9` **从未生效**（OOM 重试分支漏传参数，日志里 12 个 train 全部 `Batch used: 8` 就是铁证），且 `--iou` 在 Ultralytics 里根本不是"正样本匹配阈值"而是 NMS 阈值。所以原文档中"Phase 2 = IoU 0.9 优于 Phase 3 = IoU 0.7"的整个对比实验**在方法学上不成立**。

> **最有价值的单项发现**：Step9 的**「竖棍形幻觉框」问题与三级降级形状先验算法**（修复前 **196/2827 = 6.9%** 的图片最终输出是错误形状的框）。这个发现**在原文档里几乎完全缺失**，但它是"面积最大"这一赛制规则被模型利用（**reward hacking**）的典型案例，也最直接地解释了为什么单框模型反而比多框模型更容易拿高分。
>
> **遗憾的是**：Step9 的产物没有应用 Step6 已验证的 X2Paddle slice 补丁，导致它只能 CPU 推理（本地 10.81 FPS，远低于 20 门槛）—— 这个提交包若真提交上去，FPS 会不达标。而 `step9/log/` 为空，竖棍修复的效果也就此无法量化。
